# 32-bit Games on the Native Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tables for 32-bit games run natively on starlightd, and nothing in starlightd can crash a 32-bit game.

**Architecture:** At attach, starlightd records two facts about each target. `process_bits` comes from the ELF class of `/proc/<pid>/exe`. `code_bits` comes from the PE magic of the game's exe; it is resolved lazily and can be unknown at first.

- Remote calls read `process_bits`: they pick i386 `int 0x80` and the i386 registers, and choose a thread by code segment.
- Pointers, the assembler, disasm and Lua read `code_bits`.
- Speed refuses when `code_bits` is 32.
- The desktop passes `code_bits` into its routing check, and checks the scripts again at session start if the bitness changed.

**Tech Stack:** Rust (starlightd, iced-x86, mlua), TypeScript (engine, desktop/Electron, indexer), vitest, cargo test, gcc `-m32 -nostdlib` for an i386 test target, i686 mingw + Proton 11 for the live check.

**Spec:** `docs/superpowers/specs/2026-11-25-32bit-games-design.md`

## Global Constraints

- Every 64-bit behavior is unchanged. Every existing Rust and vitest test passes without edits, except tests that assert the exact shape of the `attach` result, which may gain fields.
- vitest always runs with `--maxWorkers=2`; the indexer package also needs `--minWorkers=1`.
- New RPC error codes:
  - `unsupported_target` = **-32015**;
  - `target_not_ready` = **-32016**.
  - Remote-call failures keep using the existing `ptrace_failed` (-32012). The spec's name `remote_call_failed` means this existing code (ruling: no new code, same contract as today).
- The speed refusal text is exactly: `Game speed doesn't work with 32-bit games yet.`
- The `target_not_ready` text is exactly: `The game is still starting; try again in a moment.`
- i386 syscall numbers: `mmap2` = 192, `munmap` = 91. The `mmap2` offset is in pages.
- The `int 0x80` site is the bytes `CD 80`, searched in `[vdso]` first, then in an r-x i386 libc mapping.
- Code segments: `cs == 0x33` is 64-bit code and `cs == 0x23` is 32-bit code.
- When `code_bits` is 32, every allocation is below 4 GiB.
- Wine's own exes never decide `code_bits`. These are matched case-insensitively: `start.exe`, `wineboot.exe`, `services.exe`, `winedevice.exe`, `plugplay.exe`, `explorer.exe`, `rpcss.exe`, `svchost.exe`, `conhost.exe`.
- Never touch the user's running game:
  - live checks use only our own targets, in a throwaway prefix with its own `STEAM_COMPAT_*` env;
  - they kill only processes they started.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Rulings made while planning

- **`hook.rs` stays 64-bit.** Its only user is speed, which refuses 32-bit games, so re-encoding hooks at 32 bits would be dead code (YAGNI). If speed for 32-bit games comes later, it does this then.
- **`patch` makes no remote calls,** because it writes through `/proc/<pid>/mem`. So the guard doesn't cover it. Writing 32-bit code is safe once the assembler produces 32-bit bytes.
- **`aob_exec` is engine-side** (alloc + assemble + patch). It is covered by guarding `alloc`.
- **The i386 integration target is freestanding** (`-nostdlib`), because this machine has no i386 glibc. That also exercises the `[vdso]` site path.

## Review Focus

1. **A WoW64 game attached before its exe is mapped.** `code_bits` must stay unknown. Alloc, assemble, pointer and speed must refuse with -32016 rather than act at 64 bits. Test in Task 1.
2. **Remote calls on threads whose code segment doesn't match the call.** Such a thread must never get a `syscall` or `int 0x80` it can't run. If no thread matches, the call is refused before any register changes. Test in Task 4.
3. **A 32-bit pointer chain whose pointer + offset passes 0xFFFFFFFF.** It must wrap at 32 bits, as CE does, and never produce a 64-bit address. Test in Task 3.
4. **A table that passes routing at 64 (bitness unknown) on a game that turns out to be 32-bit.** It must be checked again at 32, and must move to Cheat Engine if that check fails, before any cheat runs. Test in Task 8.
5. **A 64-bit game whose exe is only found late.** Speed must say "still starting" (-32016) and not crash. Plain reads and scans keep working throughout. Test in Task 2.
